# Changing a package-manager backend

A backend has four responsibilities. A change to any one of them usually
requires touching the others, and the ones people forget are the last two.

| Responsibility | Where | Forgotten? |
| --- | --- | --- |
| **Validate** the lockfile is one hermeto understands | `project.py` | rarely |
| **Parse** it into package records | `project.py` | rarely |
| **Download** and checksum the artifacts | `main.py` | sometimes |
| **Rewrite** the lockfile for the hermetic build | `main.py` | **usually** |

The rewrite path is the one that bites. Hermeto does not just read the
lockfile — it emits a modified copy with every `resolution.tarball` pointed at
a local file, and the build then runs against that copy. If you change how a
lockfile is **read** without changing how it is **written**, hermeto will
accept the input, produce a correct SBOM, and emit a lockfile the package
manager rejects. The unit tests will pass. Only an integration scenario
catches it.

## Before changing anything

1. Read the design document: `docs/design/<package-manager>.md`. It is the
   record of why the backend works the way it does.
2. Read the user documentation: `docs/<package-manager>.md`. If your change
   alters what a user can do, this file changes in the same PR.
3. Read the existing tests end to end:
   - `tests/unit/package_managers/<lang>/<pm>/`
   - `tests/integration/<pm>/scenarios/`
4. Check `hermeto/core/resolver.py` if the change affects dispatch.

## The four invariants — never break these

From `AGENTS.md`, in priority order:

1. **No arbitrary code execution.** Never shell out to the ecosystem's own
   tool to resolve, install, or normalise anything. If a change seems to
   require running `pnpm`, `npm`, or `yarn`, stop — the design forbids it, and
   the whole SBOM guarantee rests on that.
2. **Checksum validation.** Verify checksums where the lockfile supplies them.
   Where it does not, the SBOM must mark the dependency accordingly. Never
   silently skip verification.
3. **Lockfile-driven.** Hermeto parses pre-resolved lockfiles. It never
   resolves dependencies itself. Do not add a fallback that guesses a version,
   queries a registry for metadata, or fills in a missing field.
4. **SBOM accuracy.** Download only what the lockfile declares; report exactly
   what was downloaded.

## Adding support for a new lockfile version

Work through all five, in order:

1. **Widen the version gate.** Find the function that validates the version
   (for pnpm: `_ensure_lockfile_version_is_supported` in `project.py`). Decide
   deliberately whether the new version is *also* supported or *instead of*.
   Keep the rejection path for genuinely unsupported versions, and keep its
   error message naming what *is* supported.
2. **Handle format changes in the reader.** A new lockfile version may change
   the document structure, not just field names — a multi-document YAML
   stream, a new top-level key, a relocated section. `yaml.safe_load` raises
   on a multi-document stream; `yaml.safe_load_all` is the multi-document
   reader.
3. **Handle format changes in the writer.** Whatever structure you accepted on
   read must survive the rewrite. `yaml.safe_dump` emits one document; a
   multi-document input needs `yaml.safe_dump_all` and the documents in their
   original order. Confirm by round-tripping a real lockfile.
4. **Add an integration scenario.** Copy the newest existing scenario
   directory, replace `in/` with a lockfile generated by the new tool version,
   and regenerate `out/` with `nox -s generate-test-data`. Never hand-edit
   `out/bom.json` or `out/.build-config.yaml`.
5. **Update the docs.** `docs/design/<pm>.md` records *why* the new format is
   handled the way it is. `docs/<pm>.md` records which versions a user can
   expect to work.

## Error messages

Every error a user can hit must say what to do next. Compare:

```text
Unsupported lockfileVersion: '10'
```

```text
Unsupported lockfileVersion: '10'. Hermeto supports lockfileVersion 9
(pnpm 9 through 11). See docs/pnpm.md for the supported version matrix.
```

The second is the standard. `AGENTS.md`: *"Error messages must be friendly and
actionable. Suggest a solution or where to look for help, link to docs when
suitable."*

## Experimental backends

A backend still under development uses the `x-` prefix (`"type": "x-foo"`).
Do not drop the prefix as part of an unrelated change — promoting a backend
out of experimental is its own decision with its own PR.

## A new backend is a bigger task

A brand-new package manager needs a design document first, from
`docs/design/package-manager-template.md`. Do not start writing a new backend
without one merged.

## Security

If you find what looks like a security vulnerability while reading backend
code, **stop**. Do not fix it and do not mention it in a commit. Alert the
human operator and point at `SECURITY.md`.
