# Update a minumum required version of python

## Prerequisites

- user specified python versions; minimal required version and target
  version  for upgrading (for example 3.11, or 3.14 etc); if not, ask user
  to specify them
- verify if `pyupgrade` package is installed by calling

```bash
pyupgrade -h
```

  and based on the response either continue or install `pyupgrade` package
  by calling

```bash
pip install pyupgrade
```

  command.

- access older commits which contains python upgrade
  (from version 3.9 to 3.10):
  - [first commit](https://github.com/hermetoproject/hermeto/commit/c9acd3d3d5bd2210ab9f3fccf7a78827fe0043ce)
  - [second commit](https://github.com/hermetoproject/hermeto/commit/146b1d93ed29931d3625b90e89a3fc837c13fd34)
  - [third commit](https://github.com/hermetoproject/hermeto/commit/427eb636cd700c236c5c76c8ca09bf5bc691972f)
- keep in mind that those are old commits and current state of the project
  can be different
- scan all the places where is the update needed for context

## Task 1 - rewriting python version

Location of files can be different. Always look for exact match, and if you
can not be sure, ask user. Always double check if there are more potential
new places/strings suited for replacement. Make all changes localy directly
in Hermeto project, do not make any copies of repository and do not commit
files.

Files with a fixed Python versions that should not be modified, skip these
completely:

- /hermeto/tests/integration/pip/scenarios/pip_e2e/in/Containerfile
- /hermeto/tests/integration/pip/scenarios/pip_e2e_wheels/in/Containerfile
- /hermeto/docs/design/binary-platform-filtering.md

If the target version of python is bigger than the python version inside
`/hermeto/Dockerfile`, ask user if he want to update the versions in it.
Otherwise do not rewrite this file at all.

File location candidates that should be modified:

- /hermeto/pyproject.toml
  - requires-python
  - target-version
  - python_version
  - remove old version from `classifiers` array
- /hermeto/noxfile.py
  - uv pip compile at three or more places
  - python:[current version]-alpine
- /hermeto/.github/workflows/gating.yaml
  - matrix.python-versions: remove old version from array
  - if: matrix.python-version
  - python:[current version]-slim
- /hermeto/.github/workflows/docs.yaml
  - python-version at two or more places
- /hermeto/.github/workflows/renovate-pipcompile.yml
  - container: image:
  - one run command contains three python versions `-python=`
- /hermeto/CONTRIBUTING.md
  - multiple `nox -s python-`
- /hermeto/docs/pip.md
  - example of generated requirements.txt file,
    `This file is autogenerated by pip-compile with Python` line

## Task 2 - regenerating requirement files

In project root there are 3 files that are autogenerated.

- /hermeto/requirements.txt
- /hermeto/requirements-build.txt
- /hermeto/requirements-extras.txt

Delete these files and generate them again using:

```bash
nox -s pip-compile
```

If the command fails, jump into virtual environment by calling:

```bash
source venv/bin/activate
```

and call the command again.

## Task 3 - upgrading python files with pyupgrade

Call

```bash
pyupgrade -h
```

to find out possible versions for upgrade; for example for target
version 3.11 it would be `--py311-plus` argument, and the command
would be

```bash
find . -name '*.py' -exec pyupgrade --py311-plus {} +
```

Call and replace `--py311-plus` with correct target version:

```bash
find . -name '*.py' -exec pyupgrade --py311-plus {} +
```

This will call the `pyupgrade` command on every file with `.py` extension.

## Task 4 - reverting unwanted changes

If the user specified which changes they do not want, scan all local
files and revert those parts back to previous state.
For example: `Optional[X]` was changed to `X | None` by pyupgrades, but
user specified he does not want this change; so you will look at all
local changes, and revert these changes. If user did not specified what
to revert, make a summary of changes and ask if he want to revert some
parts.
